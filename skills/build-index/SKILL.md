# Build Index

Produce a single compact index of all projects so retrieval reads **one small file** to
shortlist, then opens only the top candidates in full. On a large knowledge base (dozens
of projects) this is the main speed and accuracy win — the ranker matches on declared
frontmatter fields instead of re-reading every case study.

This skill assumes projects already carry frontmatter (see `enrich-kb`). It reads that
frontmatter; it does not derive it.

## Only real content counts

Ignore `README.md` and `_template.md`, and skip placeholder-only files. The index lists
real projects only.

## What to write

Write `bid-resources/projects/INDEX.md`, **overwriting** any previous version (it is a
generated cache, not user content — say so at the top). One entry per project, carrying
its slug (the filename) plus its frontmatter fields:

```md
# Projects Index

> Generated by build-index. Do not edit by hand — re-run the organizer to refresh.

## acme-dashboard.md
- title: Acme Realtime Dashboard
- tech: react, node, postgres, websockets
- domain: fintech
- problem_tags: dashboard, real-time, data-viz
- has_outcome: true
- url: https://acme.example.com

## legacy-migration.md
- title: Legacy Billing Migration
- tech: python, django, postgres
- domain: 
- problem_tags: migration, billing
- has_outcome: false
- url: 
```

Rules:
- Include **every** real project — do not drop any.
- Carry each field verbatim from the file's frontmatter. If a field is empty in the
  source, leave it empty here; do not fill it in.
- The filename is the key — `find-evidence` uses it to open the full file for the
  projects it shortlists.

## Steps

1. List real project files and read each one's frontmatter block only.
2. If a real project has **no** frontmatter, note it in your report (it can't be indexed
   reliably) and recommend running `enrich-kb` — do not invent frontmatter for it here.
3. Write `INDEX.md` with one entry per project as above.
4. Report the project count indexed and any files skipped for missing frontmatter.
